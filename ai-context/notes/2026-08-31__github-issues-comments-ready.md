Проблема не воспроизводится: `onetableDocLister::getJSON()` вызывает `prepare` до формирования API-ответа, переданный closure выполняется, а добавленное поле `aaaaa` попадает в JSON при `api=1`.

## #386 — pub_date не попадает в item['date'] в режиме api

Классификация: NEEDS_INFO / CANNOT_CONFIRM.

```markdown
Проверил текущую реализацию на `master` (`515dce6`). По коду дефект пока подтвердить не удалось.

В режиме `api=1` поле `date` для контроллера `site_content` формируется в `core/controller/site_content.php`: источник берётся из `dateSource` (по умолчанию `pub_date`), а при ненулевом `pub_date` именно это значение должно попасть в `date`. Логика повторяет обработку HTML/debug-режима.

Отдельный нюанс `returnDLObject->getDocs`: `getDocs()` возвращает данные до вызова `site_content::getJSON()`, поэтому вычисляемого поля `date` там быть не должно — оно создаётся только при формировании API-ответа.

Чтобы локализовать отличие Evo 3.1.24, нужен минимальный вызов DocLister с параметрами `controller`, `api`, `dateSource`, `dateFormat`, `selectFields`, а также SQL выборки из debug-журнала и сырые значения `pub_date`/`createdon` для одного проблемного документа. В первую очередь стоит проверить, что `selectFields` действительно включает `pub_date`.
```

## #342 — Фильтр по >, >=, <, <=

Классификация: REPRODUCIBLE.

```markdown
Проверил #342 на текущем `master` (`515dce6`) — проблема остаётся актуальной.

В `core/filterDocLister.abstract.php` для операторов `>`, `>=`, `<`, `<=` и алиасов `gt`, `egt`, `lt`, `elt` значение всё ещё приводится через `floatval()`. Для строковых дат это меняет смысл значения: например, `floatval('2019-01-01')` превращается в `2019.0`, поэтому корректно сравнивать строковые даты и текстовые TV этими операторами нельзя.

После открытия issue логика этих операторов не менялась, коммитов с привязкой к #342 нет. Регрессионных тестов для `gt/lt/egt/elt` также нет.

В обсуждении были предложены разные контракты — сохранить текущие числовые операторы и добавить отдельные строковые/датовые либо ввести типизированные операторы. Перед исправлением нужно выбрать вариант с учётом обратной совместимости. Для legacy-проекта безопаснее не менять семантику существующих числовых операторов, а добавить явно типизированные варианты и покрыть оба поведения тестами.
```

## #320 — Не учитывается offset при подсчёте количества документов

Классификация: REPRODUCIBLE / NOT_FIXED_BY_NAMED_COMMIT.

```markdown
Проверил #320 на текущем `master` (`515dce6`) — исходная проблема всё ещё воспроизводится по коду.

`offset` участвует в `LIMIT` при получении документов, но общее количество берётся через `getChildrenCount()` без вычитания `offset`. Пагинатор затем использует это значение напрямую, поэтому число страниц рассчитывается как `ceil(total / display)`, хотя при заданном offset ожидается расчёт по доступному остатку.

В истории есть коммит `0de5c08` с сообщением `Fix #320`, но его изменение относится к обработке `stripslashes($filter->get_where())` и не исправляет подсчёт страниц с `offset`.

Регрессионного теста для сочетания `paginate`, `display` и `offset` сейчас нет. Для исправления сначала нужно закрепить ожидаемый контракт тестом: должен ли offset уменьшать только число отображаемых документов и `total`, либо также влиять на другие метаданные пагинации.
```

## #319 — DLMenu и openIds при нескольких родителях

Классификация: NEEDS_INFO.

```markdown
В issue отсутствуют шаги воспроизведения, пример вызова DLMenu и ожидаемый/фактический результат, поэтому подтвердить конкретный дефект пока невозможно.

На текущем `master` все id из `openIds` вместе с текущим документом объединяются в общий `activeBranch`, а глубина берётся по самой глубокой из открытых веток. Эта логика не менялась после открытия issue.

Уточните, пожалуйста, что означает «несколько родителей» в данном сценарии, и приложите:
- минимальный вызов DLMenu с `parents`, `documents`, `openIds`, `hideSubMenus` и `maxDepth`;
- структуру дерева (`id` и `parent` задействованных документов);
- ожидаемый и фактический HTML или JSON.

После этого можно определить, является ли поведение ошибкой объединения веток либо ожидаемым следствием общего `activeBranch`.
```
